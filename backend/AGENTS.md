# Инструкции для Backend-агента Odyssey

Корневой `AGENTS.md` задаёт общие правила. После согласования задачи самостоятельно выполняй правки и безопасные проверки в её пределах, работая только в `backend/`. Связанные контракты frontend можно изучать в режиме чтения. Изменения frontend и инфраструктуры требуют отдельного согласования и отдельной задачи. В рамках backend-задачи не выполняй commit, push, merge, release или deploy.

## Карта существующего backend

- `go.mod` и `go.sum` определяют зависимости. Модуль указывает Go 1.27, IBM Sarama v1.50.3 и `xdg-go/scram`. Обработчики и сборщики находятся в одном Go-пакете. Сохраняй `net/http` и IBM Sarama. Изменение архитектуры, замена Kafka-библиотеки, добавление или установка зависимостей требуют согласования.
- `main.go` регистрирует REST-маршруты, выбирает bootstrap и содержит `createAdminClient` и `sendJSONError`. `topics.go` обслуживает список, детали и операции изменения топиков. `search.go` читает сообщения и партиции. `consumer_groups.go` обслуживает список и детали групп, включая участников и offsets.
- `kafka_auth.go` регистрирует конфигурацию подключения в памяти по bootstrap и строит настройки Sarama. `app_health.go` проверяет доступность backend, `health.go` проверяет подключение к Kafka, `cluster_health.go` формирует состояние кластера для Overview, включая ISR.
- `overview.go` формирует сводки. `throughput.go`, `topics_panel.go`, `consumer_lag_panel.go` и `events_panel.go` ведут историю в кольцевых буферах в памяти процесса. `metrics_range.go` разбирает временной диапазон. `brokers_panel.go` формирует сведения о брокерах и использует локальный Docker для части данных. `certificates.go` обслуживает панель сертификатов. `updater.go` содержит проверку версии, запуск настроенного обновления и SSE. При проверках не запускай обновление.

## REST и выбор кластера

- До правки изучи регистрацию маршрута, соседние обработчики, структуру ответа, потребителей API и создание Sarama-клиента. Переиспользуй подходящие обработчики и точки создания клиентов. Не создавай параллельный путь подключения с другой конфигурацией для той же операции.
- Сохраняй пути, HTTP-методы, статусы и структуру JSON, включая ошибки. Изменение контракта согласовывай заранее. Проверяй метод, параметры пути и запроса, размер тела и пределы чтения. Устанавливай заголовки до записи статуса. Возвращай клиенту безопасное сообщение об ошибке и сохраняй диагностический контекст без чувствительных данных.
- `getBootstrapFromRequest` учитывает `X-Kafka-Bootstrap`, серверную переменную `KAFKA_BOOTSTRAP_SERVERS` и локальное значение по умолчанию. Считай заголовок и остальные клиентские поля недоверенными. Для затронутого маршрута проверяй синтаксис адресов, допустимость фактических сетевых назначений и права на кластер и действие. Применяй ограничения и к адресам брокеров, полученным из Kafka metadata, если меняешь политику исходящих подключений. Заголовок и CORS сами по себе прав не предоставляют.
- Используй один и тот же проверенный профиль для запроса, клиента и результата. При изменении идентификации учитывай коллизии профилей с одинаковым bootstrap, смену авторизации и удаление профиля. Проверяй, что данные, соединения и конфигурации не переходят между кластерами. В публичном `main.go` маршруты зарегистрированы напрямую. Не предполагай наличие общего middleware авторизации.

## Sarama, Kafka и безопасность

- Сверяй новую операцию с версией протокола в конфигурации Sarama, возможностями используемой версии брокера и моделью развёртывания. Для KRaft опирайся на Kafka API и метаданные брокеров. Не вводи зависимость от ZooKeeper. Различай брокер, leader партиции, назначенные replicas и ISR. Для lag различай committed offset группы и log end offset партиции. Учитывай отсутствующий commit, изменение лидера и ребалансировку.
- Сохраняй подтверждённые способы подключения из `buildKafkaConfig`: PLAINTEXT, mTLS и SASL PLAIN, SCRAM и GSSAPI поверх TLS. Учитывай TLS в существующих путях конфигурации. Отдельного публичного режима с именем `TLS` в этом переключателе нет. Не отключай проверку сертификатов и имени узла, не понижай требования TLS и не добавляй небезопасные обходы.
- Не читай реальные пароли, ключи, токены или другие секреты без отдельного разрешения. Не пиши их в логи, ответы REST и тестовые артефакты. Опасные операции, включая удаление топика, изменение конфигурации действующего кластера и сброс offsets, выполняй только по явному разрешению владельца. В рамках разработки проверяй такие пути на уровне обработчика с подставной зависимостью.

## Отмена, параллелизм и метрики

- Передавай `r.Context()` в операции, принимающие контекст. Ограничивай время подключения, чтения, записи и повторов там, где API Sarama не принимает контекст. Проверяй отмену в циклах и выход при закрытии потока. Назначай владельца клиента, admin-клиента, consumer и потребителя партиции. Закрывай ресурсы на всех путях, включая частичную инициализацию, с учётом зависимостей между ними.
- Действующие сборщики запускаются лениво по bootstrap и имеют методы `Stop`. При изменении жизненного цикла проверяй защиту от повторного запуска, остановку таймеров и горутин, конкурентный доступ к реестрам и снимкам. Не держи mutex при сетевом вызове, если это не требуется для корректности. При расширении сбора заранее определи лимиты по кластерам, рядам и запросам. Управляемая остановка при удалении профиля и при завершении сервера — направление улучшения, а не гарантированное свойство текущей реализации.
- Используй измерения Kafka или подтверждённого внешнего источника. Привязывай метрики к кластеру и, где применимо, к конкретному брокеру. Для CPU, RAM и диска локальный Docker подходит только при подтверждённом соответствии контейнера брокеру. Для VM и удалённых брокеров требуется подтверждённый источник. Не подставляй вымышленные значения или нули вместо недоступных метрик.
- Сохраняй смысл throughput и lag, единицы, временные метки, интервал сбора и границы диапазона. Различай ноль, недоступность и ошибку. Учитывай retention и compaction при интерпретации offsets. Оцени стоимость обхода брокеров, топиков, партиций и групп, прежде чем увеличивать частоту или объём опроса.

## Проверки и отчёт

- Проверка `PR Checks` выполняет `go test ./...`, `go vet ./...` и `go build ./...` из `backend/` на последнем патче ветки Go из `go.mod`. Проверка Go stable неблокирующая и повторяет команды только при различии версий. Текущий workflow `ci-cd.yml` запускает сборку backend при push в `main`. Dockerfile отдельно собирает Linux-бинарник с `CGO_ENABLED=0`.
- Для локальной проверки используй совместимый Go и доступные зависимости. Если команда требует скачивания toolchain или модулей, согласуй это заранее. При отсутствии `*_test.go` результат `go test ./...` подтверждает проверку пакета без сценарных тестов. Для правок с конкурентным доступом используй `go test -race ./...` при наличии тестов и поддерживаемого окружения с race detector.
- Для новых регрессий предлагай табличные unit-тесты, проверки HTTP через `httptest` и подставные зависимости для ошибок Sarama. Отдельно проверяй ошибку подключения, таймаут, отмену, TLS/mTLS/SASL, смену кластера и закрытие клиентов. Интеграционные проверки запускай только на согласованном тестовом кластере. Разрушительные Kafka-операции в рамках проверок запрещены.
- Пояснения, новые комментарии и отчёты пиши на русском языке. В итоге перечисляй изменённые файлы, результаты сборки, фактически выполненные тесты, неподтверждённые сценарии и оставшиеся риски. Успешная сборка и прогон без тестовых файлов не подтверждают работу функции.
