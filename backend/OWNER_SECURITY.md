# Локальный владелец установки

**Статус:** серверная защита профилей реализована; GSSAPI намеренно закрыт по
согласованному решению до появления контроля фактического транспорта KDC.
Работа ведётся в изолированной ветке. Переход работающей установки на эту
версию требует отдельного согласования и первоначальной настройки владельца.

Frontend требует вход владельца до загрузки профилей. Перенос старых настроек
из localStorage выполняется после входа; при частичной ошибке исходные записи
сохраняются, повтор использует идемпотентные ключи. Во время обновления следует
закрыть старые вкладки Odyssey: старый frontend не должен писать прежний формат
localStorage параллельно миграции. Это не требует остановки Kafka.

## Первоначальная настройка

- `ODYSSEY_DATA_DIR`: отдельный приватный каталог данных backend.
- `ODYSSEY_KEY_FILE`: путь к новому файлу ключа вне каталога данных. Родительский
  каталог ключа должен существовать и быть доступным только пользователю процесса
  (на Windows также допускается SYSTEM).
- `ODYSSEY_PUBLIC_ORIGIN`: точный origin браузерного приложения, без пути,
  завершающего слеша, параметров или учётных данных.
- Локальная команда `kafka-backend owner-init` запрашивает пароль через stdin,
  отключая отображение ввода в терминале Linux/Windows. Не передавать пароль
  аргументом, переменной окружения или командой, сохраняемой в истории shell.
- Обычный запуск без готового владельца и ключа завершается отказом.
  Открытого HTTP-маршрута первоначальной регистрации нет.

Повторная инициализация не перезаписывает данные и ключ. При частичной ошибке
остатки сохраняются для локального разбора администратором; автоматического
восстановления пустой установки нет. Резервная копия должна включать данные и
соответствующий ключ, хранимые раздельно. Утрата ключа не компенсируется паролем.
Данные не должны находиться в Git, frontend public, образе или общедоступном томе.
Защита предполагает доверенный родительский каталог и учётную запись ОС.

## HTTP

- `POST /api/auth/login`: JSON с паролем; при успехе серверная cookie и CSRF-токен.
- `GET /api/auth/session`: получить CSRF-токен существующей сессии.
- `POST /api/auth/logout`: отозвать сессию; требуется CSRF.
- Другие API требуют сессию, кроме backend health и безопасного GET version/check.
- Изменяющие запросы требуют точный Origin и заголовок `X-CSRF-Token`.
- Сессии ограничены 8 часами и 30 минутами простоя; после перезапуска нужен вход.
- До пяти попыток входа в минуту на установку, одна проверка Argon2id одновременно,
  не более 16 действующих сессий. Rate limit может временно ограничить и владельца.
- HTTP разрешён только для loopback-origin и loopback-клиента. Сетевой доступ
  требует прямой HTTPS с `ODYSSEY_TLS_CERT_FILE` и `ODYSSEY_TLS_KEY_FILE`.
- Заголовки reverse proxy не подтверждают HTTPS или адрес клиента. Поддержка
  TLS termination на proxy пока отсутствует; небезопасного обхода нет.

Cookie HttpOnly, SameSite=Strict, Secure при HTTPS, без Domain. Пароли, ключи,
CSRF-токены и cookie нельзя писать в журналы. CSRF-токен frontend должен держать
в памяти, а не в localStorage. Права Kafka по-прежнему ограничены Kafka ACL;
серверное обновление остаётся запрещённым. Создание, удаление и изменение
конфигурации топиков разрешаются только владельцу с действующей сессией,
выбранным серверным профилем и CSRF для изменений. ACL API не реализован.
Изменяющие Kafka-запросы также требуют `X-Kafka-Profile-Revision`: устаревшая
или отсутствующая ревизия отклоняется с 409 до создания клиента. Это защищает
вкладку от выполнения старого действия после изменения профиля другой вкладкой.

## Серверные профили

`/api/kafka-profiles` требует сессию и CSRF для изменений; старый
`/api/clusters/config` закрыт с 410. Для Kafka используется `X-Kafka-Profile-ID`;
bootstrap больше не выбирает сохранённые учётные данные. Неизвестный ID и старая
ревизия не получают запасного PLAINTEXT-подключения. HTTP-ответы содержат только
метаданные. Профили с одинаковыми адресами независимы, сохраняются в owner.enc.
Невалидный кандидат или ошибка записи не удаляет прежнюю конфигурацию.
Пока исходный список localStorage не перенесён полностью, frontend блокирует
изменение/удаление профилей, чтобы повтор переноса не конфликтовал с редактированием.
localStorage не предоставляет транзакции двух ключей: серверные записи подтверждаются
первыми, выбранный ID меняется перед удалением старого списка; при сбое браузерного
хранилища исходный список сохраняется для повторной попытки.

Серверные списки `ODYSSEY_KAFKA_ALLOWED_NETWORKS` (CIDR через запятую) и
`ODYSSEY_KAFKA_ALLOWED_PORTS` (порты через запятую) по умолчанию пусты: соединения
запрещены. Kafka bootstrap и advertised endpoints проходят проверку фактического
IP и порта с закреплением IP при Dial, включая TLS-чтение сертификатов.
gokrb5 открывает DNS/TCP/UDP к KDC самостоятельно. Надёжно перехватить эти
назначения через Sarama Dialer нельзя, поэтому GSSAPI закрыт до инициализации
библиотеки для HTTP и сохранённых профилей, без переключателя обхода.
Пути krb5.conf и keytab из HTTP запрещены. Старый код GSSAPI сохранён для
будущего подключения только серверных доверенных конфигураций и транспорта.
Не нужно настраивать реальные Kerberos-секреты для этой версии: их чтение
и KDC-соединения не выполняются. Старый профиль GSSAPI не удаляется и не
переводится на PLAINTEXT; его миграция требует полноценной поддержки GSSAPI.

Хранилище рассчитано на один процесс backend. Межпроцессная блокировка и
гарантии сохранения последнего rename при отключении питания пока не реализованы.
Не запускать второй экземпляр с тем же каталогом данных и ключом.

## Проверки

Новые тесты используют исключительно временные каталоги, синтетические пароли и
httptest; не обращаются к Kafka. На шаге 24Д дополнительно выполнен Windows
тестовый бинарник: сценарии DACL, хранилища и HTTP прошли на синтетических данных.
Это не проверка реального терминального ввода, серверного HTTPS или подключения
к действующей Kafka: эти сценарии требуют отдельной эксплуатационной проверки.
