# Переход на локального владельца и серверные Kafka-профили

Изменения backend и frontend поставляются совместно в одном PR. Отдельный коммит
дизайна сохраняет уже подготовленные Settings, Sidebar, Header и панели Overview.
Промежуточный backend-коммит нельзя устанавливать со старым frontend: прежний
маршрут регистрации профилей по bootstrap закрыт намеренно.

## До обновления

1. Согласовать эксплуатационное окно и целевое окружение с владельцем установки.
   Подготовка PR не означает разрешение на deployment или остановку процессов.
2. Сохранить проверенную резервную копию конфигурации установки. Не помещать
   Kafka-пароли, сертификаты, приватные ключи и browser storage в Git или issue.
3. Выбрать отдельный приватный `ODYSSEY_DATA_DIR` и `ODYSSEY_KEY_FILE` вне него.
   Доступ к каталогу ключа имеет только пользователь backend (Windows: также SYSTEM).
   Родительские каталоги и учётная запись ОС должны быть доверенными.
4. Задать точный `ODYSSEY_PUBLIC_ORIGIN`. Для сетевого доступа нужен прямой HTTPS
   с серверными `ODYSSEY_TLS_CERT_FILE` и `ODYSSEY_TLS_KEY_FILE`. Доверие к reverse
   proxy ещё не реализовано; заголовки Forwarded не являются обходом проверки TLS.
5. Явно разрешить нужные Kafka-сети и порты через
   `ODYSSEY_KAFKA_ALLOWED_NETWORKS` и `ODYSSEY_KAFKA_ALLOWED_PORTS`.
   Политика распространяется и на адреса из metadata. Пустые списки запрещают
   подключения. Не расширять их на весь интернет ради успешного подключения.
6. Убедиться, что с выбранным хранилищем будет работать только один backend.
   Межпроцессная блокировка и гарантия последнего rename после отключения питания
   пока отсутствуют. Не использовать общий каталог данных для нескольких реплик.

## Первоначальный владелец

Локально выполнить `kafka-backend owner-init` с настроенными путями данных и ключа.
Пароль вводится через stdin, без аргумента командной строки или переменной окружения.
В терминалах Linux/Windows отображение ввода отключается. Открытого HTTP setup нет.
Повторная регистрация не перезаписывает владельца, профили или ключ.

Не удалять хранилище при ошибке запуска и не создавать новый ключ вместо потерянного.
Ключ шифрования не восстанавливается из пароля владельца. Для восстановления нужна
проверенная копия данных и соответствующего ключа; хранить их раздельно.
Команды сброса владельца и ротации ключа в эту минимальную модель не входят.

## Перенос browser-профилей

1. Закрыть старые вкладки Odyssey, которые могут сохранять прежний localStorage.
   Kafka останавливать для миграции настроек не требуется.
2. После согласованного запуска новой версии войти как владелец. До входа Kafka UI
   не монтируется и учётные данные не отправляются backend.
3. Frontend переносит записи через защищённый API с сессией и CSRF. У каждого профиля
   появляется случайный серверный ID, независимо от bootstrap и способа подключения.
4. Старый список сохраняется до подтверждения всех записей. Частичная ошибка не
   удаляет исходные конфигурации; повтор использует стабильные ключи миграции.
   До полного переноса изменение и удаление профилей заблокированы.
5. После успеха список с секретами удаляется из localStorage. Остаются выбранный
   серверный ID и обычные настройки интерфейса. API возвращает только метаданные.

localStorage не даёт транзакции двух ключей. Если запись выбранного ID или удаление
старого списка завершится ошибкой, возможна повторная миграция; серверные данные
уже сохранены. Не удалять старые записи вручную ради скрытия ошибки. Изменение
исходного списка во время переноса приводит к отказу, а не перезаписи новых данных.

Профили Kerberos/GSSAPI сохраняются в исходном списке при отказе переноса.
gokrb5 самостоятельно использует DNS/TCP/UDP к KDC, поэтому исполнение GSSAPI
временно закрыто до защищённого транспорта и серверной политики krb5/keytab/KDC.
Существующий код сохранён; переменной обхода нет. Автоматического PLAINTEXT нет.

## Права и совместимость

- Это единственный владелец установки, без системы пользователей и Enterprise RBAC.
- Cookie HttpOnly и SameSite; Secure при HTTPS. CSRF-токен остаётся в памяти UI.
- Обновление приложения через HTTP остаётся запрещённым даже владельцу.
- Создание/удаление топиков и изменение их конфигурации требуют сессию, CSRF,
  ID и ожидаемую ревизию профиля. Kafka ACL сохраняют свои ограничения.
- Изменение профиля другой вкладкой приводит к 409 до создания Kafka-клиента.
  Нужно перечитать профиль, а не повторять старое административное действие.
- ACL API отсутствует; capability `manageAcl` остаётся false.
- PLAINTEXT, TLS/mTLS, SASL PLAIN/SCRAM и несколько bootstrap сохраняются.
- Неизвестный профиль или ошибка расшифрования не включают запасное подключение.

## Проверки перед выпуском

Автотесты проверяют владельца, сессии, CSRF, перенос и отказы с синтетическими
данными, подставными клиентами и временными каталогами. Linux/Windows build и
Windows unit-тесты не подтверждают работу конкретных TLS/SASL-настроек кластера.
До выпуска требуется отдельно согласованная проверка реального тестового Kafka,
прямого HTTPS, входа через браузер, сохранения профилей после перезапуска и
резервного восстановления. Не проверять отказы остановкой продуктивных брокеров.

Откат не должен открывать прежние неавторизованные REST-операции. Перед откатом
согласовать безопасную версию, совместимость формата данных и сетевую изоляцию;
не удалять ключи, профили и исходные browser-конфигурации автоматически.
