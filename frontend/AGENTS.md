# Инструкции для frontend Odyssey

Корневой `AGENTS.md` задаёт общие правила. Эти инструкции уточняют работу внутри `frontend/`. Если задаче требуется изменение REST-контракта на сервере, опиши его для согласования. Правки по frontend-задаче ограничивай каталогом `frontend/`.

## Структура React

- `src/main.tsx` подключает глобальные провайдеры, `src/App.tsx` задаёт маршруты, `src/components/layout/Layout.tsx` объединяет навигацию, заголовок и экран состояния кластера. При правках сохраняй существующие URL и поведение переходов.
- Перед созданием компонента проверь `src/components/common/` (`PanelInfo`, `Dropdown`, `ThemeDropdown`, `Sidebar`), `src/components/ui/select/KSCSelect.tsx` и `src/components/page-header/` (`PageHeader`, `TimeRangePicker`, `RefreshIntervalPicker`). Учитывай назначение и доступность компонента при переиспользовании.
- Разделяй отображение, состояние, запросы и типы по мере роста функции. Пример — `src/pages/consumer-groups/` с каталогами `components/`, `hooks/`, `services/` и `types/`. Выноси самостоятельные части страницы из монолитного компонента, когда у них появляются собственные данные или сценарии. Избегай массовой миграции JSX и замены архитектуры в рамках локальной правки.

## Дизайн и локализация

- В `src/styles/themes.css` используй `var(--panel-radius)` для скругления панелей, `--bg-primary`, `--panel-bg`, `--card-bg` и `--input-bg` для поверхностей, `--text-primary` и `--text-secondary` для текста, `--border-color` для границ, `--accent-color`, `--success-color` и `--danger-color` для акцентов и статусов. Используй значения через `var(...)`. Сохраняй все темы `src/contexts/ThemeContext.jsx` и не вводи дублирующие токены.
- Размещай стили рядом с функциональной областью по её соглашениям. Проверяй узкую и широкую раскладку, длинные названия топиков и групп, читаемость таблиц и графиков. Для интерактивных элементов обеспечь доступные имена, управление клавиатурой и видимый фокус. Дублируй статус текстом, когда он обозначен цветом. Изменение глобального оформления и новые визуальные зависимости согласовывай заранее.
- Подключай строки через `react-i18next` и существующий namespace `common` из `src/i18n/index.js`. Добавляй один и тот же ключ в `src/locales/ru/common.json` и `src/locales/en/common.json`. Проверяй подписи, подсказки, сообщения об ошибках и пустые состояния при переключении языка через `LanguageContext`.

## Overview и Recharts

- Бери диапазон и механизм ручного и автоматического обновления из `src/contexts/DashboardControlsContext.tsx`. Следуй композиции в `src/pages/Overview.tsx`. Для относительных диапазонов и абсолютных границ `from`/`to` проверяй, что throughput, активность топиков, lag и события используют один выбранный интервал.
- Синхронизируй курсор через общий `hoverTime` и функции `src/pages/overview/components/overviewTime.ts`. Сопоставляй точки по времени, поскольку ряды могут иметь разные интервалы и пропуски. Сохраняй соответствие цвета идентификатору серии при фильтрации, сортировке и обновлении. Для топиков переиспользуй `getStableTopicColor` из `topicColor.ts`.
- Сохраняй загруженные снимки отдельно по ID кластера и применимому диапазону. При возврате показывай снимок этого кластера и обновляй его по действующим правилам. При отсутствии снимка показывай загрузку или пустое состояние. Различай реальный ноль, отсутствие точек и ошибку повторного запроса.

## Запросы и типы

- Сверяй метод, путь, параметры, заголовки и JSON с существующим REST-контрактом. Для кластерных запросов учитывай выбор в `src/contexts/ClusterContext.tsx` и заголовок `X-Kafka-Bootstrap`. Общий механизм запросов через `fetch` находится в `src/hooks/useKafkaFetch.js`. Запросы Consumer Groups находятся в `src/pages/consumer-groups/services/consumer-groups.api.ts`, типы ответов — в соседнем `types/consumer-groups.types.ts`. Для Topics есть `src/pages/topics/hooks/useTopics.js`, для получения версии — `src/services/versionService.js`. В Overview часть запросов находится в странице и панелях.
- Отменяй запрос на размонтировании или смене его параметров, если используемый клиент это поддерживает. Перед применением ответа сверяй актуальность кластера, диапазона и запроса, включая обработку ошибок. Обрабатывай таймауты, HTTP-ошибки и недоступность Kafka. Для рабочего UI используй реальные ответы API. Сообщения Kafka и пользовательские значения отображай как текст, без вставки необработанного HTML.

## Новые страницы, панели и проверка

- Изучи ближайшие экраны и общие компоненты. До реализации страницы или панели согласуй с владельцем концепцию, размещение, структуру компонентов, источники данных, необходимые API и состояния экрана. После согласования самостоятельно вноси правки, исправляй ошибки и выполняй проверки в утверждённых границах.
- При установленных зависимостях `npm test` запускает Vitest один раз, а `npm run test:watch` следит за изменениями. `npm run build` и `npm run build:public` выполняют одну и ту же публичную сборку. `npm run dev` запускает Vite в режиме `public` с прокси `/api` на `localhost:8080`. `npm run preview` обслуживает ранее собранный frontend. Проверка `PR Checks` запускает тесты и сборку. Отдельные скрипты линтинга и проверки типов отсутствуют. Устанавливай зависимости только по согласованию.
- Для затронутого UI проверь загрузку, пустой ответ, ошибку, недоступность Kafka и восстановление. Для Overview проверь ручное и автоматическое обновление, оба вида диапазонов и переход A → B → A при задержанном ответе. Для визуальных изменений проверь темы, RU/EN и клавиатурную навигацию. Отдельно укажи результат сборки, реально выполненные тесты и неподтверждённые сценарии.
- Комментарии в новом коде, пояснения и отчёты пиши на русском языке.
