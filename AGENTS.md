# Инструкции для ИИ-агентов Odyssey

## Область действия

Эти инструкции действуют во всём публичном репозитории `odyssey-kafka`. Odyssey предоставляет веб-интерфейс для мониторинга и управления Apache Kafka. Frontend использует React, TypeScript/JavaScript и Vite. Backend использует Go, `net/http` и IBM Sarama. Frontend и backend взаимодействуют через REST API.

Работай только в пределах публичного репозитория `odyssey-kafka`. Соблюдай границу между Open Source и Enterprise. Не переноси в публичный репозиторий приватный код, конфигурацию, ресурсы или функциональность Enterprise. Сохраняй публичный контракт `@odyssey/registry` и пустой публичный реестр Enterprise-модулей.

Перед изменением конфигурации сборки проверь публичный режим Vite `public`, который используют скрипты из `frontend/package.json`.

## Порядок работы

1. До редактирования найди точки входа, вызывающий код, зависимости и затронутые контракты. Для сквозной задачи проследи путь от UI до обработчика REST и вызова Kafka. Проверь, какие сценарии опираются на текущее поведение.
2. Сохраняй существующую архитектуру и обратную совместимость, если владелец явно не согласовал иное. Учитывай REST API, маршруты, сохранённые пользовательские настройки и данные предыдущих версий. Если требуется несовместимое изменение, заранее опиши последствия, миграцию и откат.
3. Для новой страницы сначала представь концепцию и план. Укажи цель, сценарии пользователя, место в навигации, источники данных, состояния интерфейса, изменения REST и способ проверки. Дождись явного согласования владельца перед реализацией.
4. После согласования конкретной задачи самостоятельно выполняй необходимые локальные правки, проверки и исправления в её утверждённых границах. Отдельное согласование каждой мелкой правки не требуется. Для действий, перечисленных в разделе о побочных эффектах, действуют отдельные требования.
5. Ограничивай diff рамками задачи. Переиспользуй существующие компоненты, хуки, типы и серверные функции там, где они сохраняют требуемое поведение. Установку или добавление зависимостей и связанные изменения файлов фиксации версий согласовывай заранее.
6. Пиши пояснения, отчёты и комментарии в новом коде на русском языке. Сохраняй существующие программные идентификаторы, ключи API и локализации в оригинальном виде.

## Карта репозитория

- `frontend/src/App.tsx` и `frontend/src/components/layout/` отвечают за маршрутизацию и общую компоновку. `frontend/src/contexts/` содержит состояние уровня приложения.
- `frontend/src/pages/` содержит страницы и их логику. Для организации связанной функциональности смотри `frontend/src/pages/consumer-groups/` с компонентами, хуками, сервисом API и типами.
- `frontend/src/styles/themes.css` определяет токены тем. Переводы находятся в `frontend/src/locales/ru/` и `frontend/src/locales/en/`.
- `backend/main.go` регистрирует REST-маршруты. Обработчики, настройка Sarama и сборщики метрик находятся в доменных файлах `backend/`.
- `.github/workflows/` содержит проверки сборки, публикацию, деплой и вспомогательные workflows. `docker-compose.yml`, `k8s/` и `terraform/` описывают окружения.

## Frontend

- Следуй дизайн-системе Odyssey. Переиспользуй общие компоненты и существующие CSS-токены, включая `var(--panel-radius)` для скругления панелей. Запрещено произвольно создавать переменные оформления, дублирующие существующие токены. При изменении системы тем сверяй CSS, допустимые идентификаторы темы и меню выбора.
- Для новых пользовательских строк добавляй ключи и переводы RU и EN по принятой структуре. Проверяй читаемость обеих локализаций и управление затронутыми элементами с клавиатуры.
- Учитывай загрузку, пустой ответ, ошибку, недоступность Kafka и переключение активного кластера. Сохраняй ранее загруженные данные каждого кластера при переключении и используй их при возврате к нему. Храни данные раздельно по идентификатору кластера. При смене кластера или параметров запроса не применяй устаревшие ответы к текущему экрану и не смешивай данные разных кластеров.
- Сохраняй правила назначения цветов линиям графиков, семантику временных диапазонов, состояния подключения и правила ручного и автоматического обновления метрик. Изменения этих правил требуют согласования и проверки затронутых сценариев.
- Для связанных графиков Overview синхронизируй вертикальный курсор по времени. Сохраняй цвет каждой серии при обновлении данных, смене диапазона и изменении порядка серий. Применяй единый выбранный временной диапазон ко всем связанным графикам и списку событий.
- Рабочий интерфейс должен отображать фактические данные Kafka. Если данных нет, покажи соответствующее состояние интерфейса. Используй синтетические данные только в тестах и явно изолированных демонстрационных сценариях.

## Backend, REST и Apache Kafka

- Сохраняй согласованные HTTP-методы, пути, статусы и формат JSON. Для нового или изменённого маршрута проверь валидацию, ограничения объёма запроса и ответа, обработку ошибок и права на действие над выбранным кластером.
- Считай клиентские параметры недоверенными. При изменении выбора кластера учитывай, что bootstrap влияет на исходящие подключения backend. Не расширяй доступ к сетевым адресам, кластерным данным или операциям записи без согласования.
- Сохраняй проверку сертификатов и действующие требования к TLS, mTLS и SASL. Запрещено отключать проверку TLS-сертификатов, ослаблять ограничения безопасности или внедрять небезопасные обходные решения ради успешной сборки или подключения. При изменении подключения проверяй поведение затронутых способов аутентификации. Возвращай ошибки без учётных данных и другого чувствительного содержимого.
- Определяй владельца каждого клиента, consumer и admin-клиента Sarama. Закрывай открытые ресурсы на всех путях завершения, включая частичную инициализацию и ошибку. Ограничивай время сетевых операций. При изменении сборщика проверяй отмену, остановку таймера и завершение фоновой горутины.
- Для метрик сохраняй смысл, единицы, источник, период сбора и привязку к кластеру. Различай нулевое значение, отсутствие данных и ошибку сбора. Учитывай нагрузку при обходе топиков, партиций и групп.
- Различай доступность backend, доступность подключения к Kafka и здоровье Kafka-кластера. Изменение одного из этих сигналов проверяй вместе с его потребителями в UI.

## Секреты и операции с побочными эффектами

- Читай приватные ключи, пароли, токены, сертификаты и файлы окружения с секретами только при отдельной необходимости и после явного разрешения владельца. Для анализа сначала используй код, схемы конфигурации и безопасные примеры.
- Не выводи секреты в логи, отчёты, ответы API, фикстуры или диффы. При изменении хранения профилей исключай попадание секретов в браузерное хранилище.
- Выполняй `commit`, `push`, `merge`, `release`, `deploy` и разрушительные операции с Kafka или инфраструктурой только по явному разрешению владельца на конкретное действие. Удаление топиков, сброс offsets и изменение конфигурации действующего кластера требуют такого же разрешения.
- Для проверок с записью в Kafka используй отдельно согласованное изолированное окружение с синтетическими данными. Перед запуском проверь цель подключения и эффекты операции.

## Проверки и отчёт

После изменения выполни доступные безопасные проверки в рамках разрешённой задачи. Сверяй команды с текущими файлами проекта и учитывай их побочные эффекты. Сборку frontend через `npm run build` и backend через `go build ./...` запускай в соответствующем каталоге при наличии нужного окружения и зависимостей. Запускай относящиеся к изменению тесты и проверки типов, если они настроены. Успешная сборка подтверждает возможность сборки. Корректность поведения подтверждай отдельными проверками. Отдельно указывай фактически выполненные тесты и сценарии, которые остались неподтверждёнными.

Для правок UI проверяй затронутые темы, локализации и состояния экрана. Для правок API проверяй успешный ответ, ошибки и совместимость с существующими потребителями. Для изменений опроса Kafka проверяй задержки, ошибки подключения и смену активного кластера. Если проверка недоступна или требует отдельного разрешения, укажи причину в отчёте.

Перед завершением сверяй diff с задачей. Итоговый отчёт на русском языке должен содержать:

- список изменённых файлов и назначение каждого изменения;
- описание diff и его влияние на API, UI, хранение данных или Kafka, если применимо;
- результаты сборок и других проверок, фактически выполненные тесты и неподтверждённые сценарии с причинами;
- оставшиеся риски, ограничения и действия, требующие решения владельца.
